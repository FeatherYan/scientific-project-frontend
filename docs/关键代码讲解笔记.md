# 科研项目管理平台 MVP：关键代码讲解笔记

这份文档的目标不是覆盖所有文件，而是帮你抓住最值得讲的几个入口。面试时只要把这几块讲顺，项目就会显得很完整。

## 1. 路由与权限入口

文件：

- `src/router/routes.tsx`
- `src/permission/routeGuard.tsx`

这部分最值得讲，因为它把“页面结构”和“权限控制”连在了一起。

### 你要看什么

- 路由按角色分组
- 普通用户和管理员的访问范围不同
- `RouteGuard` 统一处理未登录、无权限、放行三种情况
- 首页不是固定路径，而是根据角色跳转

### 你可以怎么讲

> 路由设计上，我没有把所有页面平铺，而是按角色权限做了分组。未登录访问受保护页面会被守卫拦截，登录后再根据角色跳到默认首页。这样路由天然就是权限入口。

### 重点关注

- `RoleHomeRedirect`
- 普通用户路由组
- 管理员路由组
- 通知页的公共受保护路由组

## 2. 登录态与权限派生

文件：

- `src/store/slices/authSlice.ts`

这部分体现你对“全局状态边界”的理解。

### 你要看什么

- 登录成功后保存 token、role、userInfo
- 根据 role 生成 `permissions`
- 持久化到本地存储
- 退出登录时清空状态

### 关键逻辑

```ts
loginSuccess(state, action) {
  state.token = action.payload.token
  state.role = action.payload.role
  state.userInfo = action.payload.userInfo
  state.isAuthenticated = true
  state.permissions = [...ROLE_PERMISSION_MAP[action.payload.role]]
  setAuthStorage(state)
}
```

### 你可以怎么讲

> 我在登录成功后不只是保存 token，还会根据角色派生出权限列表。这样后面的菜单、按钮和路由守卫都能直接消费统一的权限数据。

## 3. 动态菜单

文件：

- `src/permission/menu.ts`
- `src/layout/BasicLayout/index.tsx`

这是很典型的中后台能力点。

### 你要看什么

- 菜单不是写死两份，而是根据角色和权限过滤
- 布局层只负责消费菜单结果
- 当前高亮菜单会根据 pathname 自动计算

### 你可以怎么讲

> 我把菜单生成逻辑和布局展示逻辑拆开了。权限模块负责产出当前用户可见菜单，布局层只管渲染，这样职责更清晰，也便于后续扩展成更复杂的菜单体系。

## 4. React Query 业务封装

文件：

- `src/hooks/useProjects.ts`

这一层最能体现你不是在页面里“直接写请求”。

### 你要看什么

- 项目列表、详情、我的申报分别用不同 query key
- 创建、保存、提交、删除用 mutation
- mutation 成功后统一失效刷新相关缓存

### 你可以怎么讲

> 页面层不直接调接口，而是通过业务 hooks 拿查询和 mutation。这样缓存策略、失效逻辑、错误处理都能集中在 hooks 层，页面会更薄。

### 重点理解的点

- 为什么 query key 要稳定
- 为什么 mutation 成功后要失效相关列表和详情
- 为什么服务端状态不放 Redux

## 5. 申报表单页

文件：

- `src/pages/project/form.tsx`

这是用户侧最核心的页面，也是最适合面试细讲的页面。

### 你要看什么

- 同一页面承载“查看”和“编辑”
- 草稿和已退回可编辑，其他状态只读
- 保存草稿与提交申报是两条不同业务动作
- 页面需要同时处理表单初始值、字段校验、保存、提交流程

### 你可以怎么讲

> 这个页面我没有拆成两个页面，而是根据业务状态切换成编辑态或只读态。这样可以减少重复代码，也更符合中后台项目里“同一条记录在不同状态下能力不同”的特点。

### 面试加分点

- `查看` 和 `编辑` 入口统一，能力由状态决定
- `保存草稿` 和 `提交申报` 的业务含义不同

## 6. 我的申报列表

文件：

- `src/pages/project/mine.tsx`

这部分很适合讲“权限 + 状态”的组合控制。

### 你要看什么

- 所有状态统一保留“查看”
- `提交` 仅草稿可用
- `删除` 仅草稿可用
- 列表操作区尽量避免语义重复

### 你可以怎么讲

> 我后来把“查看详情”和“编辑”合并成了统一入口，避免两个按钮跳到几乎相同的页面。列表里只保留业务上真正不同的动作，用户认知会更简单。

## 7. 审批详情页

文件：

- `src/pages/approval/detail.tsx`
- `src/hooks/useApprovalDetail.ts`

这是管理员侧最值得讲的页面。

### 你要看什么

- 详情展示和审批动作在同一个页面闭环完成
- 审批通过 / 退回都走 mutation
- 成功后更新审批状态，并刷新相关缓存

### 你可以怎么讲

> 审批详情页不仅是详情展示页，也是管理员执行审批动作的核心页。通过和退回都会触发 mutation，并联动刷新审批列表、我的申报和通知数据。

## 8. Mock 业务联动

文件：

- `src/mocks/handlers/project.ts`
- `src/mocks/handlers/notification.ts`
- `src/mocks/utils/storage.ts`

这部分能体现你对“没有真实后端时，怎样尽量模拟真实业务”的理解。

### 你要看什么

- 发起申报、保存草稿、提交申报、审批通过、退回申请人这些动作都在 handler 里模拟
- 审批动作会联动生成通知
- mock 数据通过 localStorage 持久化

### 你可以怎么讲

> 我没有只做静态假数据，而是用 MSW 去模拟真实接口行为。这样前端请求链路、状态流转和通知联动都能按真实工程的方式跑起来。为了避免刷新丢状态，我又给 mock 数据加了 localStorage 持久化。

## 10. 面试时可以主动强调的亮点

- 不是只做页面展示，而是打通了申报、审批、通知的完整业务闭环
- 权限控制不是单点，而是覆盖路由、菜单、按钮三层
- Redux Toolkit 和 React Query 职责边界清晰
- 表单页通过业务状态统一承载查看和编辑
- MSW 不只是返回假数据，还模拟了状态流转和通知生成
- 为了演示稳定性，额外补了 mock 持久化和重置演示数据
