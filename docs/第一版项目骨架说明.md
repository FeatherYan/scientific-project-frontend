# 科研项目管理平台 MVP

## 第一版项目骨架说明

这份文档用于说明第一版骨架阶段已经完成的内容，以及面试时需要重点掌握的架构设计、关键代码入口和表达方式。

当前阶段的目标不是实现完整业务，而是先搭建一个适合中后台项目继续演进的前端工程骨架。这样后续无论是登录鉴权、动态菜单、列表页、复杂表单，还是审批流模块，都可以在统一结构上继续实现，而不会在中途推翻重来。

## 1. 这一版做了什么

第一版已经把 Vite 默认模板替换为中后台项目常见的分层结构，核心目录包括：


## 2. 为什么先做骨架，不先写业务页

这是面试时很重要的表达点。

可以这样说：

> 这个项目是典型中后台场景，业务模块较多，如果一开始直接写业务页面，后面很容易出现请求方式不统一、权限逻辑散落、路由结构混乱的问题。所以我先把应用骨架搭好，包括状态层、请求层、权限层、布局层和路由层，确保后续每个业务页面都接在统一规范上。

核心原因有三个：

- 让技术方案更稳定，避免后续返工
- 让业务页面开发有统一约束
- 让整个项目更适合面试讲解

---

## 3. 当前项目的分层思路

### 3.1 全局状态、服务端状态、页面状态怎么分工

这是中后台面试高频题。

我的建议表达是：

> 我把状态分成三类。身份类全局状态放 Redux Toolkit，服务端数据放 React Query，页面交互状态放页面组件内部。

具体划分如下：

#### Redux Toolkit

只管理全局且跨页面共享的身份信息：

- token
- 当前用户信息
- 当前角色
- 当前权限集合
- 是否已登录

不把列表数据、详情数据放进 Redux。

#### React Query

用来管理服务端数据：

- 项目列表
- 项目详情
- 审批列表
- 审批详情
- 通知列表

以及配套的：

- 缓存
- loading
- error
- refetch
- mutation 后的失效刷新

#### 页面状态

只放页面局部状态：

- 搜索条件输入
- 分页页码
- 弹窗开关
- 当前 tab
- 表单临时交互状态

### 3.2 为什么不用 Redux 管所有数据

可以这样答：

> 因为项目列表、审批详情这类数据本质上是服务端状态，不适合放进 Redux 手动维护。React Query 天然更适合处理缓存、重新请求和异步状态。Redux 更适合存登录态、角色和权限这种全局身份信息。

## 4. 当前权限方案怎么设计

第一版采用的是 `RBAC`，这是最适合当前 MVP 的方案。

### 4.1 角色

- `user`
- `admin`

### 4.2 权限码

当前已经定义了几类权限码：

```ts
project:list
project:create
project:edit
project:delete
project:submit
project:viewMine
approval:list
approval:detail
approval:approve
approval:reject
notification:list
```

### 4.3 权限控制分三层

这是你面试时一定要说清楚的重点。

#### 第一层：路由权限

控制某个页面是否可以访问。

例如：

- 没登录不能进系统页
- 普通用户不能进审批页
- 管理员不能进普通用户申报页

#### 第二层：菜单权限

控制左侧菜单显示哪些入口。

例如：

- 普通用户看到“项目申报 / 我的申报 / 通知中心”
- 管理员看到“审批管理 / 通知中心”

#### 第三层：按钮权限

这一层第一版还没有落地到按钮组件，但方案已经预留好了。

后续会控制：

- 用户端的“新建 / 编辑 / 删除 / 提交”
- 管理员端的“通过 / 退回”

### 4.4 为什么菜单也要做权限控制

可以这样回答：

> 因为只有路由守卫还不够。如果用户虽然进不去页面，但菜单仍然能看到不该看到的入口，体验和安全边界都不够好。所以我把菜单也建立在同一套权限判断之上，让页面访问和菜单展示保持一致。

## 6. 面试时你可以怎么介绍第一版

你可以用下面这段思路来讲。

### 6.1 一分钟版本

> 这个项目第一版我没有急着写业务页面，而是先把中后台项目的基础骨架搭起来了。包括 React Router 的路由结构、Redux Toolkit 的登录态管理、React Query 的 Provider、axios 的统一请求层、基于角色和权限的路由守卫，以及动态菜单和主布局。这样后面无论是用户端的项目申报，还是管理员端的审批流，都能在统一结构下继续开发。

### 6.2 两分钟版本

> 第一版的重点是把工程结构和核心基础设施搭好。我先把项目拆成 request、api、hooks、store、permission、pages、layout 这些层，让页面层不直接耦合请求层和权限逻辑。权限上采用 RBAC，先定义 user 和 admin 两个角色，再建立角色与权限码映射，然后在路由守卫和动态菜单里复用同一套权限判断。状态管理方面，我把登录态和用户信息放到 Redux Toolkit，把服务端业务数据预留给 React Query，把搜索条件和弹窗之类的交互态放在页面内部。这样做的目的是让后续业务模块接入时结构清晰，也方便面试时说明为什么这么分层。

## 7. 面试高频问题整理

### 7.1 为什么 Redux Toolkit 和 React Query 要同时用

答法：

> 因为两者解决的问题不同。Redux Toolkit 管全局身份信息，比如 token、用户信息、角色和权限。React Query 管服务端数据，比如项目列表、审批详情和通知列表，它更适合处理缓存、异步状态和重新请求。

### 7.2 为什么菜单要动态生成

答法：

> 因为不同角色看到的菜单不同，动态菜单可以让菜单展示和路由权限保持一致，避免出现页面进不去但菜单还显示的问题。同时把菜单建立在统一权限判断上，也更便于维护。

### 7.3 为什么一开始不做后端返回菜单

答法：

> 这是一个面试展示用 MVP，当前重点是把前端权限模型、路由结构和模块分层讲清楚。前端先维护静态路由和菜单配置，已经足够覆盖大多数中后台面试问题，也更容易讲明白。如果后续项目复杂度增加，再扩展成后端驱动菜单。

### 7.4 为什么登录页现在是角色快捷登录

答法：

> 因为第一版的目标是先验证登录态流转、角色切换、默认首页跳转和权限控制，而不是先做完整的登录业务。当前先用角色快捷登录把鉴权骨架跑通，后续接入 mock auth 接口后再替换成真实表单提交。

### 7.5 为什么要先做统一请求层

答法：

> 因为中后台项目接口很多，如果页面里直接散落写请求，后面很难统一处理 token 注入、错误提示和响应结构。所以我先把 request 层做好，再让 api 层和 hooks 层都基于它扩展。
