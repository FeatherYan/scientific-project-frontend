# 第七版通知中心说明

这一轮的目标是把增强模块落地，并把整个 MVP 的业务链条补完整：

```txt
用户发起申报
  -> 管理员审批
  -> 审批结果生成通知
  -> 用户在通知中心查看结果
```

## 2. 为什么通知模块值得做

因为它能把这个 MVP 从“单页面功能展示”提升成“完整业务链展示”。

如果没有通知，项目虽然有申报和审批，但用户对审批结果的感知还停留在主动去列表里查看状态。

加上通知之后，就可以更完整地讲：

> 用户提交申报后，管理员完成审批，系统会主动反馈结果给用户。

这很像真实中后台系统，也更适合面试表达。

## 3. 当前通知中心怎么设计

### 3.1 通知筛选

支持三种维度：

- 关键词
- 通知类型
- 阅读状态

### 3.2 通知列表项内容

每条通知展示：

- 标题
- 类型标签
- 已读 / 未读状态
- 通知正文
- 通知时间
- 关联项目入口

### 3.3 交互行为

支持：

- 单条标记已读
- 点击“查看关联项目”时自动标记已读
- 再跳转到对应申报记录

这套交互比较贴近真实消息中心的处理方式。

## 4. 审批动作和通知是怎么联动的

这一轮最关键的点就是这个。

管理员审批动作发生后，会在 mock 层追加通知数据：

### 审批通过

新增通知内容示例：

> 你提交的某项目已审批通过，请关注后续安排。

### 退回申请人

新增通知内容示例：

> 某项目已退回，请根据审批意见补充后重新提交。

这样用户进入通知中心，就能看到审批后的系统反馈。

## 5. 当前模块的技术链路

### 通知列表

```txt
通知中心页筛选变化
  -> useNotificationList(params)
  -> api/notification.ts
  -> axios request
  -> MSW /api/notifications
  -> React Query 返回数据
  -> 列表渲染
```

### 标记已读

```txt
点击标记已读 / 查看关联项目
  -> useMarkNotificationRead
  -> /api/notifications/:id/read
  -> invalidate notifications
  -> 列表刷新
```

### 审批触发通知

```txt
管理员审批通过 / 退回
  -> mock 审批接口修改项目状态
  -> 追加一条新的审批结果通知
  -> invalidate notifications
  -> 用户通知中心看到最新消息
```

## 7. 面试时怎么讲这一轮

### 一分钟版本

> 第七轮我实现了通知中心，并把审批动作和通知反馈串起来了。用户现在不仅可以在“我的申报”里查看状态，还可以在通知中心看到审批通过或退回的结果通知。通知页支持关键词、类型和已读状态筛选，也支持标记已读和跳转关联项目。这让整个 MVP 从申报、审批延伸到了结果反馈，业务链更完整。

### 两分钟版本

> 这一轮我实现的是增强模块里的通知中心，但它不是孤立做一个消息列表，而是把前面已经完成的申报与审批流程真正串起来。通知中心的数据通过 notification 模块独立管理，支持查询、标记已读和跳转关联项目。更关键的是，我在审批通过和退回的 mock 接口里增加了通知生成逻辑，所以管理员审批动作会直接影响用户通知中心的数据。这样用户就能通过系统主动反馈感知审批结果，而不是只靠自己去列表里刷新状态。这个模块虽然不复杂，但它能很好地体现中后台系统中的事件反馈链路。
