# 第三版补充：用户端语义纠偏说明

这次调整的核心不是新增功能点，而是修正普通用户端的信息架构，让页面职责更符合真实业务。

---

## 1. 为什么要改

你指出的问题是对的。

上一版里的“项目申报列表”实际上更像“我的申报记录”，因为它展示的是当前用户已经发起的申报数据，并且支持编辑、提交、删除等操作。

但在真实业务里，这两个概念应该分开：

- `可申报项目`：系统当前开放给用户申请的项目清单
- `我的申报`：用户自己已经创建的申报记录

如果这两个页面混在一起，业务语义会不清楚，面试时也容易被追问。

---

## 2. 这次调整后怎么划分

### 可申报项目

页面：

- `src/pages/project/list.tsx`
- `src/pages/project/detail.tsx`

职责：

- 展示系统当前开放申报的项目
- 支持关键词搜索
- 支持查看项目详情
- 支持从详情页发起申报

### 我的申报

页面：

- `src/pages/project/mine.tsx`

职责：

- 展示当前用户已经发起的申报记录
- 支持按状态筛选
- 支持草稿编辑
- 支持草稿删除
- 支持草稿或已退回项目提交

---

## 3. 路由和菜单怎么变了

### 路由

新增：

- `/projects/:id` 用于“可申报项目详情”

保留：

- `/projects/list` 现在表示“可申报项目列表”
- `/projects/mine` 表示“我的申报”

### 菜单

用户端菜单现在更合理：

- 可申报项目
- 我的申报

之前的“新建申报”菜单被去掉了，因为更合理的业务流程是：

> 用户先查看可申报项目详情，再从详情页发起申报

---

## 4. 数据层怎么分了

这次把用户端数据分成两类：

### 申报项目机会数据

文件：

- `src/mocks/data/projectOpportunities.ts`

接口：

- 获取可申报项目列表
- 获取项目详情
- 发起申报

### 用户申报记录数据

文件：

- `src/mocks/data/projects.ts`

接口：

- 获取我的申报列表
- 提交申报
- 删除草稿

这比上一版统一叫 `projects` 更符合真实业务。

---

## 5. 这次调整后的业务流程

现在普通用户端的主流程变成：

```txt
进入可申报项目列表
  -> 查看项目详情
  -> 发起申报
  -> 系统创建一条草稿记录
  -> 跳转到“我的申报”
  -> 后续再编辑 / 提交
```

这个流程比“直接在列表页就像已经有申报记录”更合理，也更容易讲清楚。

---

## 6. 面试时怎么解释这次调整

你可以这样说：

> 我在实现到列表页阶段后，重新校对了业务语义，发现“项目申报列表”和“我的申报”混在了一起。为了让用户端流程更贴近真实场景，我把它拆成了两个页面：一个是系统开放申报的项目列表，用户可以查看详情并发起申报；另一个是用户自己的申报记录列表，用来管理草稿、提交审批和查看状态。这样页面职责更清晰，业务闭环也更自然。
