# 第三版项目申报列表说明

这一轮的目标是把普通用户端最典型的中后台列表页做出来，不只是放一张表，而是把列表页里最常见的一组能力一起补齐：

- 列表请求
- 搜索筛选
- 状态标签
- 权限按钮
- 基于业务状态的操作可见性
- 提交 / 删除两个基础操作

## 2. 当前列表页的技术链路

你可以用这条链路来讲：

```txt
页面搜索条件变化
  -> useProjectList(params)
  -> api/project.ts
  -> axios request
  -> MSW mock 项目接口
  -> React Query 返回列表数据
  -> 表格渲染
```

操作按钮则是另一条链路：

```txt
点击提交 / 删除
  -> useMutation
  -> mock submit/delete 接口
  -> 成功后 invalidate projects query
  -> 列表自动刷新
```

## 3. 这一轮的重点设计

### 3.1 页面层只做页面组合

列表页里主要做的是：

- 组织搜索区
- 组织表格列
- 调用 hooks
- 响应按钮点击

而不是在页面里直接写请求细节或一堆状态判断函数。

### 3.2 权限控制和业务状态控制分开

这是面试里非常重要的一点。

操作按钮是否可用，不是只看权限，也不是只看状态，而是两者共同决定。

例如“编辑”按钮：

- 先判断当前用户是否有 `project:edit` 权限
- 再判断当前项目是不是草稿或已退回

所以最终规则是：

> 按钮可见性由权限决定，按钮可操作性由业务状态决定

这比简单写 `role === 'user'` 更适合中后台项目。

### 3.3 为什么提交和删除也一起做了

因为如果只有列表展示，没有任何 mutation，React Query 的价值就不够完整。

这一轮把提交和删除一起补上，有两个好处：

- 让列表页成为一个小闭环
- 让你面试时能讲 query 和 mutation 的区别

### 4.4 操作按钮

- 编辑

并且已经体现了：

- 权限控制

## 7. 你可能会被问到的问题

### 为什么不用 Redux 存项目列表

答法：

> 因为项目列表属于服务端数据，更适合交给 React Query 管理。它天然支持缓存、异步状态和 mutation 后刷新，而 Redux 更适合存登录态和权限这种全局身份信息。

### 为什么按钮不是直接隐藏，而是有些显示但禁用

答法：

> 因为这里有两个维度。权限不足时按钮应该直接不显示；但如果用户有权限，只是当前项目状态不允许操作，那么更适合显示为禁用，并提示原因，这样用户体验更清晰。

### 为什么把状态规则抽到工具函数里

答法：

> 因为这些规则不只列表页会用，后续表单页、我的申报页、审批详情页也可能复用。提前抽离后，页面层不会堆满业务分支，结构更清晰。
