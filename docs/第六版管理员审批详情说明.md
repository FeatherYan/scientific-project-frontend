## 2. 当前管理员审批流怎么跑

这一轮跑通的是一个简化版单人审批流：

```txt
管理员进入审批列表
  -> 查看审批详情
  -> 填写审批意见
  -> 选择“审批通过”或“退回申请人”
  -> 项目状态更新
  -> 返回审批列表
```

状态流转规则如下：

- `submitted` / `approving` -> `approved`
- `submitted` / `approving` -> `rejected`

这里没有继续拆院级、校级多级审批，是为了保持 MVP 足够清晰、易讲。

## 4. 这一轮的关键设计点

### 4.1 审批详情和用户表单详情没有共用一个页面

这是有意这样设计的。

原因是两个页面虽然都展示项目内容，但角色和动作完全不同：

- 用户页关注“查看 / 编辑 / 提交”
- 管理员页关注“审核 / 通过 / 退回”

所以我把它们拆开，避免一个页面同时背负两套角色语义。

### 4.2 审批动作通过单独 hook 管理

我没有把审批通过/退回直接写在页面里，而是抽成了：

- `useApprovalDetail`
- `useApproveProject`
- `useRejectProject`

这样做的好处是：

- 页面职责更轻
- mutation 逻辑统一
- 成功后可以统一失效刷新审批列表和项目列表

### 4.3 用户侧和管理员侧状态联动已经成立

审批动作成功后，会失效：

- `approvals` 查询
- `projects` 查询

这意味着：

- 管理员返回审批列表能看到最新状态
- 用户回到“我的申报”也能看到最新审批结果

这就是整个 MVP 里非常重要的一点：

> 管理员操作能够真实影响普通用户端看到的状态

## 6. 面试时怎么讲这一轮

### 一分钟版本

> 第六轮我实现了管理员端审批详情页，把审批流真正跑通了。管理员现在可以在详情页查看申报内容、填写审批意见，并执行通过或退回操作。技术上我把审批详情查询和审批动作分别封装成独立 hook，动作成功后会统一刷新审批列表和项目列表，所以用户侧的“我的申报”也能同步看到最新审批状态。

### 两分钟版本

> 这一轮我重点做了管理员端审批详情页，让项目从“已提交”真正进入可流转的审批流程。页面上我把信息拆成几个区域：顶部的审批概览、项目基本信息、历史审批信息、申报内容以及审批操作区。架构上，审批详情查询和通过/退回两个 mutation 都放到独立的 approval hooks 里，页面只负责组织 UI 和触发动作。业务上我做了一个简化但清晰的审批规则：只有 submitted 和 approving 状态可以继续审批，通过后流转为 approved，退回后流转为 rejected。退回操作必须填写审批意见，通过可以默认补一条通过意见。这样整个管理员侧闭环就跑通了，而且管理员操作会回写到普通用户侧的项目状态中。

## 7. 你可能会被问到的问题

### 为什么审批通过可以不填意见，退回必须填

答法：

> 因为退回需要给申请人明确修改方向，所以审批意见应当是必填；而通过时意见更多是补充说明，可以给默认值，也可以允许管理员补充。

### 为什么审批详情不复用用户表单页

答法：

> 因为两边的角色语义不同。用户页强调编辑和提交，管理员页强调审核和流转。如果强行共用，会让页面承担两套角色逻辑，反而更难维护也更难讲清楚。

### 为什么审批动作后要刷新用户侧列表

答法：

> 因为审批结果不仅影响管理员当前页面，也会影响用户在“我的申报”里看到的状态。如果不统一失效刷新，就会出现两边状态不一致的问题。
