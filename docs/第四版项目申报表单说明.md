# 第四版项目申报表单说明

这一轮的目标是把用户端从“发起申报”真正推进到“编辑草稿并提交申报”，让普通用户侧的主流程形成完整闭环。

当前用户侧流程已经变成：

```txt
可申报项目列表
  -> 查看项目详情
  -> 发起申报
  -> 系统创建草稿
  -> 进入项目申报表单页
  -> 保存草稿 / 提交申报
  -> 回到我的申报
```

## 3. 草稿保存和提交申报有什么区别

这是这一轮最值得讲清楚的点。

### 保存草稿

特点：

- 不强制校验所有字段
- 允许用户分阶段填写
- 重点是保存当前编辑进度

页面中实现方式：

- 直接读取表单当前值
- 调用 `saveProjectDraft`

### 提交申报

特点：

- 必须通过表单校验
- 必须保证关键字段完整
- 提交后状态会流转到 `submitted`

页面中实现方式：

1. 先 `validateFields`
2. 先保存一次最新表单内容
3. 再调用 `submitProject`

这个顺序很适合面试讲，因为它体现了：

> 提交动作不是单纯改状态，而是先保证数据完整，再进入业务流转

## 4. 当前表单页的关键设计

### 4.1 新建/编辑复用

虽然当前是通过“发起申报 -> 进入草稿编辑”来进入表单页，但页面本身仍然采用复用思路：

- 根据路由中的 `id` 加载草稿详情
- 用同一个页面承接草稿编辑

后续如果需要扩展成真正的“新建 / 编辑”复用，结构上也是兼容的。

### 4.2 表单值和接口值分开处理

表单里使用的是：

- `period: [startDate, endDate]`

而接口层保存时需要的是：

- `startDate`
- `endDate`

所以页面里做了显式转换：

- `toFormValues`
- `toSavePayload`

这样做的好处是页面和接口职责更清晰，不会把接口结构直接硬塞给 UI。

### 4.3 只读态处理

如果当前记录已经进入后续流程，例如：

- 已提交
- 审批中
- 已通过

那么表单会进入只读模式，并显示对应提示。

这样可以保证列表页和表单页对状态规则的理解一致。

## 7. 你可能会被问到的问题

### 为什么保存草稿不做完整校验

答法：

> 因为草稿阶段的核心目标是让用户分阶段录入，不应该要求一次性填完所有内容。完整校验更适合放在正式提交时执行，这样更符合真实申报流程。

### 为什么提交申报前还要先保存一次

答法：

> 因为用户可能刚修改了表单内容，提交前先把最新内容保存下来，再触发状态流转，可以保证后端拿到的是最终版本的数据。

### 为什么要处理只读态

答法：

> 因为已提交或审批中的记录不应该继续编辑。列表页已经基于状态做了按钮控制，表单页也应该遵守同样的业务规则，保证系统行为一致。
