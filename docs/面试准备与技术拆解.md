# 科研项目管理平台 MVP：面试准备与技术拆解

这份文档是给你面试前复习用的，不是对外文档。阅读目标有两个：

- 快速建立一条完整的讲解主线
- 把主要技术点和对应代码入口挂起来，避免只会讲概念

---

## 1. 先用一句话介绍项目

可以这样说：

> 这是一个科研项目管理平台的前端 MVP，模拟高校教师或研究生发起科研项目申报、管理员多级审批的场景。我用 React + TypeScript + Vite 搭建，前端重点实现了登录鉴权、角色权限、动态菜单、列表页、复杂表单、审批流、通知联动，以及基于 MSW 的 Mock 接口体系。

如果面试官继续追问“为什么做这个项目”，可以接：

> 我希望用一个中后台场景把前端常见的工程和业务问题串起来，而不是做一个只有页面展示的项目，所以我在架构上专门把 request、api、hooks、store、permission、pages 分层拆开，便于开发也便于讲解。

## 2. 项目的核心业务链路

### 普通用户

1. 登录
2. 查看可申报项目
3. 查看项目详情
4. 发起申报并生成草稿
5. 编辑草稿并提交
6. 在“我的申报”查看进度
7. 在通知中心接收审批结果

### 管理员

1. 登录
2. 查看审批列表
3. 查看审批详情
4. 审批通过或退回
5. 系统更新状态并生成通知

这条业务链路覆盖了中后台面试最常见的几个关键词：

- 登录鉴权
- 角色权限
- 动态菜单
- 列表页
- 复杂表单
- 状态流转
- 请求封装
- mock 接口

## 3. 项目架构怎么讲

建议你讲“分层”和“职责边界”。

### 3.1 分层结构

```txt
pages -> hooks -> api -> request -> msw / backend
```

### 3.2 各层职责

#### `request`

负责 axios 实例、拦截器、超时和统一响应处理。

关键代码：

- `src/request/index.ts`
- `src/request/interceptor.ts`

推荐讲法：

> 我把 axios 单独封装成 request 层，避免页面直接依赖请求库。后续如果要统一加 token、错误提示、接口返回格式处理，都只需要改这一层。

#### `api`

负责按业务模块拆分接口函数，不直接写页面逻辑。

关键代码：

- `src/api/auth.ts`
- `src/api/project.ts`
- `src/api/approval.ts`
- `src/api/notification.ts`

推荐讲法：

> api 层只描述“调用哪个接口、传什么参数、返回什么数据”，尽量保持纯粹，方便页面和 hooks 复用。

#### `hooks`

基于 React Query 封装查询和 mutation，把缓存、刷新、加载状态、错误处理统一收口。

关键代码：

- `src/hooks/useLogin.ts`
- `src/hooks/useProjects.ts`
- `src/hooks/useApprovals.ts`
- `src/hooks/useApprovalDetail.ts`
- `src/hooks/useNotifications.ts`

推荐讲法：

> 页面不直接调 api，而是通过 hooks 获取数据和 mutation。这样页面层会更薄，React Query 的缓存和失效策略也能集中维护。

#### `store`

只管理全局身份态，不管理业务列表。

关键代码：

- `src/store/slices/authSlice.ts`
- `src/store/index.ts`

推荐讲法：

> 我刻意没有把项目列表、审批列表放进 Redux，因为这些都属于服务端状态，更适合交给 React Query。Redux 只保留 token、用户信息、角色和权限这类跨页面共享的身份状态。

#### `permission`

统一管理路由守卫、默认首页、动态菜单和权限判断。

关键代码：

- `src/permission/routeGuard.tsx`
- `src/permission/access.ts`
- `src/permission/menu.ts`
- `src/constants/permission.ts`
- `src/constants/role.ts`

推荐讲法：

> 权限体系我分成三层：路由权限、菜单权限、按钮权限。这样既能控制访问，也能控制展示，而且不会把权限判断散落在每个页面里。

#### `pages`

只做页面组合和少量页面逻辑，尽量不直接处理底层请求细节。

关键代码：

- `src/pages/login/index.tsx`
- `src/pages/project/*.tsx`
- `src/pages/approval/*.tsx`
- `src/pages/notification/list.tsx`

## 4. 登录鉴权怎么讲

这是面试里的高频问题。

### 4.1 登录流程

登录页提交账号、密码、角色后：

1. 调用登录接口
2. 拿到 token、角色、用户信息
3. 通过 Redux 保存登录态
4. 根据角色跳转默认首页

关键代码：

- `src/pages/login/index.tsx`
- `src/hooks/useLogin.ts`
- `src/api/auth.ts`
- `src/store/slices/authSlice.ts`

你可以重点看 `loginSuccess`：

```ts
loginSuccess(state, action) {
  state.token = action.payload.token
  state.role = action.payload.role
  state.userInfo = action.payload.userInfo
  state.isAuthenticated = true
  state.permissions = [...ROLE_PERMISSION_MAP[action.payload.role]]
  setAuthStorage(state)
}
```

讲解重点：

- 登录成功后不仅保存 token，也同步生成权限列表
- 登录态做了本地持久化，刷新后仍可恢复

### 4.2 路由守卫

关键代码：

- `src/router/routes.tsx`
- `src/permission/routeGuard.tsx`

推荐讲法：

> 路由守卫会先判断是否登录，再判断角色和权限是否满足。未登录跳登录页，无权限跳 403。这样权限判断被收口在路由层，不用每个页面都重复写。

### 4.3 登录回跳

如果用户未登录时访问受保护页面，登录成功后会回到原目标页。

这部分是体验加分项，面试里很适合主动提。

## 5. 权限系统怎么讲

### 5.1 为什么选 RBAC

当前项目采用的是简化版 RBAC，而不是更复杂的 ABAC。

原因：

- MVP 更适合中后台常见实现
- 面试时更容易讲清楚
- 足够覆盖角色、菜单、按钮这几个常见权限层级

### 5.2 角色与权限码

关键代码：

- `src/constants/role.ts`
- `src/constants/permission.ts`

当前角色：

- `user`
- `admin`

权限码示例：

- `project:list`
- `project:create`
- `project:submit`
- `approval:list`
- `approval:approve`
- `notification:list`

### 5.3 三层权限控制

#### 路由权限

控制能否进入页面。

#### 菜单权限

左侧菜单根据角色和权限动态生成。

关键代码：

- `src/layout/BasicLayout/index.tsx`
- `src/permission/menu.ts`

#### 按钮权限

用 `PermissionButton` 封装是否展示按钮。

关键代码：

- `src/components/business/PermissionButton/index.tsx`

### 5.4 权限不等于可操作

这是很值得讲的一点。

例如用户有 `project:submit` 权限，不代表所有记录都能提交，还要看业务状态：

- 草稿才能提交
- 审批中不能提交
- 已通过只能查看

也就是说：

> 一个操作是否可用，通常是“角色权限 + 业务状态”共同决定的。

关键代码：

- `src/utils/project.ts`
- `src/pages/project/mine.tsx`
- `src/pages/project/form.tsx`

## 6. Redux Toolkit 和 React Query 怎么分工

这个问题很常见，建议直接背一套稳定说法。

### 推荐回答

> 我把状态分成三类：身份类全局状态放 Redux Toolkit，服务端数据放 React Query，页面交互态放组件本地 state。这样每种状态都由最适合它的工具负责，不会把 Redux 变成所有数据的仓库。

### Redux Toolkit 管什么

- token
- 当前用户
- 角色
- 权限列表
- 是否登录

关键代码：

- `src/store/slices/authSlice.ts`

### React Query 管什么

- 可申报项目列表
- 项目详情
- 我的申报
- 审批列表
- 审批详情
- 通知列表

关键代码：

- `src/hooks/useProjects.ts`
- `src/hooks/useApprovals.ts`
- `src/hooks/useApprovalDetail.ts`
- `src/hooks/useNotifications.ts`
- `src/app/providers.tsx`

### 页面本地状态管什么

- 搜索条件
- 分页
- 弹窗开关
- 表单输入中间态

## 7. 列表页和表单页怎么讲

### 7.1 可申报项目列表

关键代码：

- `src/pages/project/list.tsx`
- `src/api/project.ts`
- `src/hooks/useProjects.ts`

你可以讲：

> 这页不是“我的申报”，而是系统当前开放申报的项目池。用户可以先看项目，再决定是否发起申报，这样业务语义更清楚。

### 7.2 我的申报

关键代码：

- `src/pages/project/mine.tsx`

你可以讲：

> “我的申报”展示的是用户已经生成的申报记录。列表里统一保留“查看”入口，再结合状态决定能否提交或删除，这样用户认知会更简单。

### 7.3 申报表单页

关键代码：

- `src/pages/project/form.tsx`
- `src/types/project.ts`

推荐讲法：

> 我没有拆成两个页面，而是让同一个表单页同时承载“编辑”和“查看”，再由业务状态决定表单是否只读。这样页面复用更好，面试时也更容易讲“入口统一，能力由状态控制”。

### 7.4 保存草稿和提交的区别

这是一个很好的业务点。

推荐讲法：

> 保存草稿是阶段性保存，目标是避免用户一次填完所有内容；提交申报则会在校验通过后触发状态流转，进入审批阶段。这两个动作在业务含义上不同，所以我在前端也做了分离。

## 10. 为什么用 MSW，怎么讲

这是非常适合面试主动讲的点。

### 10.1 使用原因

- 当前是前端面试项目，没有真实后端
- 但又希望完整演示请求链路、权限、状态流转和通知联动
- MSW 可以在浏览器层模拟真实接口

关键代码：

- `src/mocks/browser.ts`
- `src/mocks/handlers/auth.ts`
- `src/mocks/handlers/project.ts`
- `src/mocks/handlers/notification.ts`

### 10.2 为什么还加了 localStorage 持久化

关键代码：

- `src/mocks/utils/storage.ts`

推荐讲法：

> MSW 默认的 mock 数据只存在运行时内存里，刷新后容易回到初始状态。为了让申报、审批、通知这条演示链路更稳定，我额外用 localStorage 做了一层前端侧持久化。这是开发和演示阶段的替代方案，真实项目里这部分会由后端数据库负责。

### 10.3 重置演示数据

关键代码：

- `src/layout/BasicLayout/index.tsx`

推荐讲法：

> 因为 mock 数据被持久化了，所以我又补了一个“重置演示数据”按钮，方便每次演示前回到统一初始状态。

## 12. 常见面试问题与推荐答法

### 问：为什么不用 Redux 管所有数据？

答：

> 因为项目、审批、通知这些数据本质上都来自服务端，属于服务端状态。React Query 天然更适合处理缓存、刷新、失效和 mutation 后同步，所以我只把身份信息放进 Redux，把业务数据交给 React Query。

### 问：为什么菜单可以动态变化？

答：

> 因为菜单不是单独写死的，而是基于角色和权限从统一配置里过滤出来的。这样路由、菜单和按钮权限可以共用同一套权限体系。

### 问：为什么申报详情和编辑没有拆成两个页面？

答：

> 我希望降低重复代码，同时把业务重点放在“状态控制能力”上，所以采用了同一个表单页承载查看和编辑，再通过状态决定是否只读。

### 问：为什么用 MSW 而不是直接写死 JSON？

答：

> 因为我想保留真实请求链路。MSW 能让 request、api、hooks、页面这条调用链完整跑起来，这比单纯写死假数据更接近真实工程。

### 问：如果接真实后端，你会怎么改？

答：

> 前端整体分层基本不需要改，主要是把 MSW handlers 替换为真实 API，并把目前 localStorage 持久化的 mock 数据逻辑移除即可。因为 request、api、hooks 已经分层好了，所以迁移成本会比较低。

## 13. 一条推荐的面试讲解顺序

如果让你现场介绍项目，可以按这个顺序：

1. 先讲业务背景和项目目标
2. 再讲整体架构分层
3. 然后讲登录鉴权和权限体系
4. 再讲用户端申报链路
5. 接着讲管理员审批链路
6. 最后讲通知联动和 MSW mock 方案

这样讲的优点是：

- 从业务到技术，结构清楚
- 面试官容易跟上
- 你自己也不容易讲乱
